\section*{Resumen ejecutivo}
\addcontentsline{toc}{section}{Resumen ejecutivo}
% =====================================================

Este informe consolida el trabajo desarrollado entre el 4 de mayo de 2026 (cierre del informe de avance 2) y el 1 de junio de 2026 sobre el proyecto \textbf{\NombreProyecto}, un wearable biométrico modular de bajo costo para monitoreo continuo de actividad física, frecuencia cardíaca, oxigenación, temperatura periférica, electrocardiografía y reconocimiento de actividad humana. La motivación, la arquitectura de alto nivel y el análisis de impacto fueron presentados en los informes anteriores y se mantienen vigentes, por lo que aquí se concentran los cambios introducidos en esta iteración.

El eje de esta entrega es la \textbf{transición de prototipo de banco a unidad wearable integrable}. Mientras que la entrega anterior demostró que los subsistemas individuales funcionan (firmware FreeRTOS de siete tareas, BLE NimBLE con cuatro características GATT, Pan-Tompkins validado offline, optimizaciones de consumo con 75\,\% de tiempo en \textit{light sleep}), esta entrega convierte esos bloques en una plataforma final consistente: el microcontrolador \textbf{Seeed XIAO ESP32-S3} sobre una \textbf{PCB carrier} propia, alojada dentro de una \textbf{carcasa paramétrica V2 impresa en PLA}, complementada por una \textbf{aplicación móvil Flutter} que reemplaza al cliente Python de testing y por un \textbf{modelo de Machine Learning embarcado (CNN 1D)} que clasifica caminata, reposo, trote y caídas en tiempo real.

Los entregables tangibles producidos durante esta iteración son:
\begin{itemize}
    \item \textbf{Firmware migrado y ejecutándose en XIAO ESP32-S3} sobre PSRAM octal, con consola por USB-Serial-JTAG, \textit{light sleep} dinámico reconfigurado para el target S3, ocho tareas FreeRTOS y refactor a una librería estática \texttt{supaclock\_app} que ordena la inicialización en fases.
    \item \textbf{Algoritmo de pasos basado en FFT} acelerada por las instrucciones PIE del Xtensa LX7 (librería ESP-DSP \cite{esp_dsp}), reemplazando al detector temporal del ESP32-C3. Se incluye una suite de simulación que verifica detección, rechazo de falsos positivos por sacudidas y filtro de histéresis.
    \item \textbf{PCB Carrier SupaClock v1}: proyecto KiCad de dos capas, ruteado bajo reglas conservadoras de fresado \textbf{LPKF ProtoMat S64} \cite{lpkf_protomat}, con cero nets sin conectar y veintiséis violaciones DRC residuales de naturaleza cosmética/footprint (no bloqueantes para fabricación).
    \item \textbf{Carcasa paramétrica V2 en OpenSCAD}: dos mitades atornilladas, taper de 2\,mm, esquinas redondeadas $r=12$\,mm y \textit{chamfer} de 1.5\,mm en seam y techo, \textit{lugs} tipo ``stadium'' de 22\,mm para correa estándar, ventanas térmicas y ópticas alineadas con la PCB. STL impresos y validados físicamente.
    \item \textbf{App Flutter} con doble interfaz (usuario clínico y desarrollador), procesamiento Pan-Tompkins 100\,\% en cliente, persistencia híbrida Hive \cite{hive_db} + Firestore y almacenamiento de trazas pesadas en Firebase Storage. Reemplaza al \texttt{supaclock\_monitor.py} como gateway BLE-móvil.
    \item \textbf{Modelo CNN 1D} entrenado sobre veintisiete sesiones IMU propias (resting/walking/running), arquitectura de tres bloques Conv1D + GAP + Dense, cuantización INT8 a 58\,KB, \textit{tensor arena} de 128\,KB en PSRAM y ejecución pinned al \textbf{Core 1} del S3 (el Core 0 queda libre para BLE, LVGL e I$^2$C).
    \item \textbf{UI rediseñada} con sistema de temas persistente en NVS (cuatro paletas seleccionables como \textit{watch faces}), tipografías Inter \cite{inter_font} regeneradas a tres pesos (16\,px, 28\,px, 56\,px) y \textit{heap} gráfica trasladada a PSRAM para descongestionar la SRAM interna.
\end{itemize}

El avance consolidado del proyecto al 1 de junio de 2026 es del \textbf{65\,\%} ponderado sobre el cronograma maestro, con la PCB carrier al 100\,\% de diseño, la carcasa al 100\,\% de modelado y primera impresión validada, el firmware sobre S3 al 100\,\% de portabilidad, el ML al 80\,\% (modelo entrenado y pipeline de inferencia operativos, recolección de la clase \textit{fall} pendiente) y la app móvil al 90\,\% de las funcionalidades planificadas. La PCB está pronta para ser fresada en el laboratorio LPKF del Departamento; el bring-up eléctrico y la validación de unidad cerrada constituyen el grueso del trabajo restante hacia el cierre del semestre.

\section{Introducción}
% =====================================================

El presente informe se estructura en torno a los tres ejes que define la rúbrica de avance 3 (Diagrama de bloques de bajo nivel --- Planificación --- Implementación y resultados), y suma un capítulo dedicado al análisis cuantitativo de los resultados y otro a los próximos pasos previos a la entrega final. Cada subsistema implementado se documenta con su motivación técnica, las decisiones de diseño tomadas, los cálculos o restricciones que las respaldan y la evidencia de validación correspondiente. Los listados de código, tablas extendidas y reportes detallados (DRC, BOM, \textit{power locks}) se desplazan al anexo para mantener la fluidez de la lectura.

La codificación cromática del estado de los bloques es la misma que se empleó en los informes anteriores: \textbf{verde} para subsistemas funcionales y validados; \textbf{amarillo} para implementaciones parciales; \textbf{rojo punteado} para bloques pendientes o cuya integración cruza un hito futuro. La nomenclatura de archivos, comandos y entornos PlatformIO sigue el repositorio Git del proyecto disponible en \texttt{github.com/ArticunoFruna/SupaClock\_IEE2463}.

\subsection{Contexto de la entrega anterior y \textit{delta} del periodo}

Al cierre del informe de avance 2 el sistema cumplía con:
\begin{itemize}
    \item Firmware FreeRTOS funcional sobre ESP32-C3 SuperMini \cite{esp32c3_ds}, con siete tareas concurrentes y mutex de bus I$^2$C, integrando BMI160 \cite{bmi160_ds} (50\,Hz, \textit{step counter} nativo), MAX30102 \cite{max30102_ds} (10\,Hz, máquina de estados SPOT con \textit{motion gating}), MAX30205 \cite{max30205_ds} (1\,Hz, $\pm$0,3\,°C contra referencia), MAX17048 \cite{max17048_ds} (1\,Hz, SOC y Vcell) y AD8232 \cite{ad8232_ds} (ADC continuo a 20\,kHz con DMA on-demand, decimación a 500\,Hz).
    \item Pan-Tompkins \cite{pan_tompkins} en Python+NumPy validado offline sobre treinta segundos de captura real (76 BPM, SDNN = 32,4\,ms), código fuente versionado en \texttt{firebase/functions/main.py} pero aún sin desplegar como \textit{Cloud Function}.
    \item BLE NimBLE \cite{nimble} con cuatro características GATT (IMU, TLV agregado, ECG streaming, RX de comandos) bajo el servicio custom \texttt{0xFF00}, \textit{advertising} a 1\,s y Modem Sleep BT habilitado.
    \item Power management dinámico con DFS 10--160\,MHz, \textit{light sleep} y tres \textit{PM locks} (ECG, NimBLE, SPI), alcanzando 75\,\% de tiempo en estado SLEEP medido con \texttt{esp\_pm\_dump\_locks}.
    \item Tres modos de energía persistentes (SPORT/NORMAL/SAVER) con ocho cadencias parametrizadas y persistencia NVS.
    \item Esquemático v1 de PCB propia para SuperMini cerrado pero no manufacturado, dado el compromiso de migración al ESP32-S3.
\end{itemize}

El período cubierto por esta entrega (28 días calendario) concentró los siguientes \textit{deltas} respecto al estado anterior:
\begin{itemize}
    \item \textbf{Migración firmware completa al XIAO ESP32-S3} (target ESP-IDF, PSRAM octal, USB-Serial-JTAG, partition table extendida a 8\,MB, sdkconfig regenerado).
    \item \textbf{Rediseño completo del PCB}, abandonando definitivamente la PCB SuperMini y produciendo el \textbf{SupaClock Carrier v1} ya en formato compatible con el LPKF del laboratorio.
    \item \textbf{Carcasa V2 paramétrica} completamente nueva, reemplazando la caja rectangular conceptual del informe anterior por un envelope estilizado con esquinas redondeadas, \textit{chamfer}, taper, \textit{lugs} de correa y \textit{button caps} impresos como pieza aparte.
    \item \textbf{Algoritmo de pasos FFT} anunciado en la entrega anterior, ahora implementado en \texttt{lib/step\_algorithm} con compilación condicional por \textit{target} y banco de pruebas en \texttt{test\_fft\_steps}.
    \item \textbf{Modelo CNN 1D} entrenado y embebido como \texttt{har\_model.tflite} (58\,KB), corriendo bajo TFLite Micro \cite{tflite_micro} con ESP-NN \cite{esp_nn} y \textit{tensor arena} en PSRAM.
    \item \textbf{App móvil Flutter} ya operativa, con autenticación Firebase, escaneo y conexión BLE, doble interfaz, procesamiento ECG en cliente y persistencia híbrida.
    \item \textbf{Refactor del firmware} que extrae las siete tareas y la inicialización del antiguo \texttt{src/tests/test\_general.c} hacia una librería estática \texttt{lib/supaclock\_app}, dejando \texttt{main.c} reducido a un \textit{stub} selector de entorno.
    \item \textbf{Rediseño de la UI} con sistema de temas dinámicos, tipografías propias y consolidación de la lógica de pantallas en un módulo \texttt{lib/supaclock\_ui}.
\end{itemize}

El resto del informe profundiza en cada uno de estos \textit{deltas} desde la perspectiva eléctrica, mecánica, de firmware y de validación.

\subsection{Estado vigente}

El diagrama de alto nivel de la entrega 1 (siete dominios: interacción, energía, sensores, MCU, interfaz local, \textit{gateway}, \textit{backend}) se mantiene estructuralmente sin cambios. Lo que sí evolucionó respecto al diagrama de bloques de bajo nivel presentado en la entrega 2 es lo siguiente:
\begin{enumerate}
    \item \textbf{El bloque MCU pasa de ESP32-C3 SuperMini a XIAO ESP32-S3} \cite{esp32s3_ds_2024} y, con ello, se reconfiguran todas las asignaciones de pines, los buses, la sección de potencia y la lista de \textit{PM locks}.
    \item \textbf{El bloque ``PCB SuperMini''} desaparece y se reemplaza por \textbf{``PCB Carrier v1''}, que es el integrador físico vigente.
    \item \textbf{El bloque ``TinyML CNN 1D''} transita de \textit{pendiente} (rojo punteado) a \textit{parcial} (amarillo, 80\,\% de implementación) gracias al entrenamiento exitoso sobre datos propios y la integración del \textit{runtime} en el firmware.
\end{enumerate}

\subsection{Cambios respecto al diagrama de la entrega anterior}

\subsubsection{MCU: del ESP32-C3 SuperMini al XIAO ESP32-S3}

La justificación cualitativa de esta migración se documentó en el avance 2. En esta entrega la migración se materializó, y los cambios concretos en el diagrama son:
\begin{itemize}
    \item \textbf{Reloj y memoria.} El XIAO ESP32-S3 ejecuta un \textbf{dual-core Xtensa LX7 a 240\,MHz} con 320\,KB de SRAM interna, 8\,MB de Flash y 8\,MB de \textbf{PSRAM octal}. Esto desbloquea dos arquitecturas críticas: alojar la \textit{tensor arena} de TFLite Micro (128\,KB) y el \textit{frame buffer} doble de LVGL \cite{lvgl} en PSRAM, y \textit{pinear} la tarea de inferencia al Core 1 sin perturbar BLE y LVGL.
    \item \textbf{Mapa de pines reasignado.} El header de la XIAO S3 expone 11 GPIO mientras el SuperMini exponía 8. Esto permitió mover el reset del ST7789 a \textit{no cableado} (reset por software vía registro) y emplear GPIO43/GPIO44 para botones y CS del display, pagando el costo de redirigir la consola serie al \textbf{USB-Serial-JTAG} integrado del módulo \cite{xiao_esp32s3_pinout}.
    \item \textbf{Sección de potencia simplificada.} Tres reguladores externos del prototipo C3 (TP4056 + DW01A + ME6211 3,3\,V) se sustituyen por la cadena integrada del propio XIAO S3 (cargador SGM40567 + buck SGM6029 $\approx$800\,mA), eliminando los \textit{brown-outs} documentados en la entrega anterior. El módulo TP4056 + DW01A se mantiene en el diagrama solo para alimentar la celda LiPo externa antes de que el XIAO entre en carga, dado que la celda LiCo 502030 no se conecta directamente al pad B+/B$-$ del módulo XIAO.
    \item \textbf{Aceleración SIMD.} El bloque ``ESP-DSP'' pasa de gris (instalado pero no usado) a verde: el algoritmo de pasos FFT y la inferencia INT8 del CNN aprovechan las extensiones PIE del Xtensa LX7 (similar a SIMD).
\end{itemize}

\subsubsection{PCB: del esquemático SuperMini al Carrier v1}

El esquemático v1 de la entrega anterior nunca llegó a \textit{Edge.Cuts} listas para fabricación. Se descartó por completo y se levantó un nuevo proyecto KiCad \cite{kicad} bajo \texttt{hardware/SupaClock\_Carrier/}, cuya finalidad es ser \textbf{fabricable en el LPKF ProtoMat S64} del laboratorio Capstone (no JLCPCB), lo que impuso reglas conservadoras:
\begin{itemize}
    \item \textit{Trace width} mínimo 0,4\,mm (vs. 0,2\,mm de JLCPCB).
    \item \textit{Drill} mínimo 0,8\,mm (vs. 0,3\,mm).
    \item \textit{Clearance} mínimo 0,4\,mm.
    \item Sin máscara de soldadura (los \textit{pads} expuestos se cubren con flux \textit{no-clean} tras el ensamblado).
    \item Sin serigrafía top/bottom (las etiquetas se colocan a posteriori con marcador permanente).
\end{itemize}

Estas restricciones explican por qué el ruteo final del carrier no se parece a una PCB JLCPCB clásica: usa pistas anchas, \textit{vías} de 0,8\,mm y aprovecha \textit{zones} extensas en el plano de masa (lado \textit{bottom}) para minimizar el \textit{milling time}. El carrier en formato DIP fue una decisión consciente: el XIAO S3 va sobre un \textit{pin socket} 1x7+1x7 doble en \textit{through-hole}, lo que permite reemplazar el módulo si llega defectuoso, reaprovecharlo para futuras revisiones y reflashear el firmware por USB sin desmontar el conjunto.

\subsubsection{TinyML: de pendiente a 80\,\%}

La motivación de la entrega anterior se transformó en implementación: el modelo CNN 1D vive ahora en \texttt{lib/har\_cnn1d/} como librería estática, integrada al \textit{build} PlatformIO y embebida en el firmware como un \textit{blob} \texttt{har\_model.tflite} de 58\,KB. El estado del bloque es \textbf{parcial (amarillo)} por dos razones operativas:
\begin{enumerate}
    \item \textbf{La clase \textit{Fall} no tiene aún datos de entrenamiento reales.} Las veintisiete sesiones disponibles (siete \textit{running}, ocho \textit{walking}, doce \textit{resting}) cubren bien las tres primeras clases; la clase \textit{fall} se complementa hoy con datos sintéticos generados a partir del modelo físico de caída libre + impacto, pero la validación contra caídas reales está agendada para la semana del bring-up del carrier.
    \item \textbf{El intérprete TFLite Micro está embebido pero la inferencia continua aún no ha sido validada con el carrier ensamblado.} En la unidad de bench actual la inferencia opera y clasifica correctamente durante caminata y reposo, pero la calidad del modelo bajo vibraciones reales no ha sido medida.
\end{enumerate}

\subsubsection{Otros cambios menores en el diagrama}

\begin{itemize}
    \item \textbf{GUI LVGL: de 7 pantallas funcionales a UI rediseñada con temas.} Las siete pantallas siguen presentes pero ahora se construyen sobre \texttt{lib/supaclock\_ui} con tipografías propias (Inter Regular 16\,px / Medium 28\,px / Bold 56\,px) y cuatro temas seleccionables desde menú (\texttt{AMOLED}, \texttt{WARM}, \texttt{SLATE}, \texttt{VIVID}), persistidos en NVS.
    \item \textbf{App móvil: de 0\,\% a 90\,\%.} El bloque ``App móvil (gateway)'' del diagrama de la entrega 2 estaba en rojo punteado. Hoy es verde funcional: la app Flutter en \texttt{app/lib/} reemplaza al \texttt{supaclock\_monitor.py} y desempeña el rol de gateway BLE+gateway clínico.
    \item \textbf{Pan-Tompkins: de Cloud Function a procesamiento en cliente.} En la entrega anterior se proyectaba desplegar el algoritmo en Firebase Cloud Functions. La decisión fue \textbf{reubicar el procesamiento en el cliente} (\texttt{app/lib/services/pan\_tompkins.dart}) para reducir la latencia a menos de 100\,ms y evitar costos redundantes en la nube, promoviendo una estrategia de funcionamiento \textit{offline-first}.
    \item \textbf{Cliente PC testing: deprecado.} El bloque \texttt{supaclock\_monitor.py} pasa a rojo punteado: sigue funcional para depuración rápida, pero su rol fue absorbido por el modo desarrollador de la app Flutter.
\end{itemize}

\subsection{Justificación de los cambios en el diseño}

\subsubsection{Procesamiento ECG en cliente vs. Cloud Function}

El informe anterior planificaba un trigger Firestore que ejecutara Pan-Tompkins sobre cada captura de ECG. Durante el desarrollo de la app móvil se evaluó este flujo en dos escenarios:
\begin{itemize}
    \item \textbf{Latencia percibida.} La toma estándar de ECG dura 30\,s. En el flujo cloud, tras la captura el usuario espera entre 2 y 5\,s adicionales por el \textit{cold start} + \textit{RTT} de la Cloud Function. En el flujo cliente, el cálculo termina en $<$100\,ms sobre los 3000 \textit{samples} recién recibidos, y la pantalla de resultados aparece sin transición.
    \item \textbf{Costos y dependencia de red.} Mover el procesamiento al cliente convierte el reporte de HRV en algo que opera de forma autónoma e independiente de la conectividad (diseño \textit{offline-first}), ahorrando costo de computación redundante en la nube.
\end{itemize}

La decisión fue mantener \texttt{firebase/functions/main.py} en el repositorio como \textit{fallback} y referencia algorítmica, pero que el camino primario para los usuarios sea \texttt{app/lib/services/pan\_tompkins.dart}. Ambos flujos ejecutan idénticos pasos de procesamiento.

\subsubsection{Algoritmo de pasos: FFT en lugar de umbral temporal}

El detector de pasos del ESP32-C3 presentaba limitaciones: sub-conteo del orden del 10\,\% y falsos positivos al agitar la mano. La migración a un análisis espectral FFT, implementado en \texttt{lib/step\_algorithm/step\_algorithm.c}, resuelve esto aprovechando el target S3. El nuevo algoritmo es estructuralmente distinto:
\begin{enumerate}
    \item Acumula 128 muestras de magnitud lineal del acelerómetro a 50\,Hz ($\approx$2,56\,s de ventana física).
    \item Solo procesa si la energía rotacional es suficiente (\texttt{max\_gyro\_val $>$ 400 LSB} $\approx 25$\,°/s), eliminando vibraciones ajenas a la caminata.
    \item Remueve el sesgo DC y aplica \textbf{ventana de Hann} vía \texttt{dsps\_wind\_hann\_f32}.
    \item Calcula la \textbf{FFT radix-2 acelerada} por PIE (\texttt{dsps\_fft2r\_fc32} + \texttt{dsps\_bit\_rev\_fc32}) en 220\,$\mu$s.
    \item Busca el pico de potencia en la banda de caminata $[0,75\,\text{Hz}, 2,75\,\text{Hz}]$ y compara contra un umbral empírico $\text{UMBRAL\_FFT} = 1\cdot10^9$.
    \item Aplica \textbf{histéresis temporal de dos ventanas}: la primera detección no descarga pasos sino que los guarda en cache; solo si una segunda ventana consecutiva supera el umbral se acumulan ambos, eliminando falsos positivos por movimientos aislados.
\end{enumerate}

\subsubsection{Carcasa V2: del \textit{box} rectangular a un envelope estilizado}

La iteración v1 era un \textit{bounding box} funcional pero estéticamente plano. El rediseño V2 introduce:
\begin{itemize}
    \item \textbf{Esquinas verticales redondeadas} con $r\_vert = 12$\,mm, aproximando la huella de un reloj clásico.
    \item \textbf{Chamfer inferior y superior} de $r\_chamfer = 1,5$\,mm mediante operación Minkowski, suavizando las transiciones.
    \item \textbf{Taper de 2\,mm} entre la base y el techo, reduciendo el perfil de ``ladrillo'' y mejorando la ergonomía.
    \item \textbf{\textit{Lugs} tipo ``stadium''} integrados, con ancho de 20\,mm para correa estándar y contrafuertes robustos de 5\,mm.
    \item \textbf{\textit{Button caps} como piezas separadas} con \textit{flange} exterior, transmitiendo la pulsación mecánica sin debilitar la carcasa.
    \item \textbf{Dimensión final 98$\times$79$\times$25\,mm}, ajustada a la PCB carrier y con cavidades interiores para alojar la batería.
\end{itemize}

Durante las pruebas iniciales se corrigieron dos fallas: se rotó la ventana del MAX30102 90° para alinearse con el PCB footprint real, y se extendió el cutter cilíndrico de los orificios laterales a 16\,mm de profundidad para atravesar por completo las paredes curvas originadas por el taper y el chamfer.

\subsection{Migración firmware al Seeed XIAO ESP32-S3}

\subsubsection{Descripción}

La migración al Seeed XIAO ESP32-S3 requirió reconfigurar el firmware para adaptarlo a un target dual-core con arquitectura Xtensa LX7, 8\,MB de Flash y 8\,MB de PSRAM octal de alta velocidad. Se adaptaron el bootloader, mapa de pines, partition table y la administración de energía para este target de hardware.

\subsubsection{Decisiones de diseño y cálculos}

Se declaró en \texttt{platformio.ini} la placa \texttt{seeed\_xiao\_esp32s3} conservando el framework \texttt{espidf}. Se habilitaron los flags \texttt{-DBOARD\_HAS\_PSRAM} y \texttt{-DARDUINO\_USB\_CDC\_ON\_BOOT=1} para inicializar la PSRAM por hardware y redirigir los logs de la consola por el puerto USB-Serial-JTAG nativo.

El mapa de pines se centralizó en \texttt{include/supaclock\_pinmap.h} (ver extracto en Sección \ref{sec:anexo_pinmap}), definiendo las reasignaciones para buses I$^2$C, SPI, ADC y GPIO de botones NEXT y SELECT. El reset del display ST7789 se configuró por software (\texttt{st7789\_driver} ejecuta la secuencia de comandos y delays correspondientes) para ahorrar un pin físico en el módulo. La partition table se extendió mediante un archivo \texttt{partitions.csv} a 8\,MB, distribuyendo espacio para dos slots OTA de 3\,MB, SPIFFS de 1\,MB y NVS de 64\,KB, dejando suficiente margen para actualizaciones inalámbricas futuras.

El \textit{light sleep} dinámico se reconfiguró de acuerdo a los requerimientos de la S3, modificando la estructura a \texttt{esp\_pm\_config\_esp32s3\_t} con rangos de frecuencia entre 40\,MHz y 240\,MHz y conservando los correspondientes PM locks para resguardar la adquisición continua del ECG.

\subsubsection{Resultados}

\begin{itemize}
    \item Compilación limpia del entorno \texttt{main\_app} sobre target esp32s3: binario final de 720\,KB.
    \item Heap libre disponible tras arranque completo: 142\,KB en SRAM interna y 7,8\,MB en PSRAM externa.
    \item Consola e interfaz de depuración operativa directamente por USB-Serial-JTAG.
    \item Cero colapsos por brown-out registrados durante pruebas de mesa de hasta 6 horas consecutivas.
\end{itemize}

\subsection{Refactor a \texttt{lib/supaclock\_app/}}

\subsubsection{Descripción}

Toda la lógica del firmware, que en el hito anterior ocupaba más de 2000 líneas en un único archivo de test general, se modularizó y extrajo en una librería estática autocontenida denominada \texttt{supaclock\_app}.

\subsubsection{Decisiones de diseño}

La librería expone únicamente una función de inicialización: \texttt{void supaclock\_app\_run(void)}. Internamente organiza la ejecución en tres fases: inicialización de sensores I$^2$C $\to$ display y GUI LVGL $\to$ stack BLE NimBLE. Se separó el struct de datos a \texttt{lib/app\_state/} bajo protección de un mutex, eliminando las variables globales. La interfaz gráfica se desacopló y reubicó bajo \texttt{lib/supaclock\_ui/}. Con esta estructura, \texttt{src/main.c} se reduce a un stub minimalista de 10 líneas, y PlatformIO compila selectivamente solo las dependencias requeridas por cada entorno de test.

\subsubsection{Resultados}

Se logró una reducción del acoplamiento del código principal, permitiendo construir entornos de depuración rápidos (como el caso de \texttt{capture\_c3} que compila un firmware de sólo 280\,KB, libre del peso de LVGL y de la PSRAM, idóneo para el ESP32-C3).

\subsection{Algoritmo de pasos basado en FFT (ESP-DSP)}

\subsubsection{Descripción}

Este bloque sustituye el detector temporal previo por una aproximación frecuencial de ventana deslizante procesada asíncronamente en el Core 1.

\subsubsection{Decisiones de diseño y cálculos}

El algoritmo se implementó en \texttt{lib/step\_algorithm/step\_algorithm.c} (ver extracto en Sección \ref{sec:anexo_pasos}). Los pasos principales son:
\begin{enumerate}
    \item Magnitud lineal $|a| = \sqrt{a_x^2 + a_y^2 + a_z^2}$ calculada con FPU de hardware.
    \item Gating rotacional: procesa la ventana de 128 muestras solo si \texttt{max\_gyro\_val $>$ 400 LSB} ($\approx 25$\,°/s) en toda la ventana, descartando vibraciones externas.
    \item Remoción de DC bias y ventaneo de Hann.
    \item FFT radix-2 y bit-reversal aceleradas por hardware vía librería ESP-DSP en 220\,$\mu$s.
    \item Búsqueda del pico de potencia espectral en la banda $[0,75\,\text{Hz}, 2,75\,\text{Hz}]$.
    \item Si el pico de potencia supera $1\cdot10^9$, se derivan los pasos del bin del espectro correspondientes.
    \item Histéresis de dos ventanas: se almacena en cache la detección inicial y solo se incrementa el contador global si existe persistencia temporal en la segunda ventana física.
\end{enumerate}

\subsubsection{Resultados}

El algoritmo fue validado con la suite de simulación \texttt{test\_fft\_steps} superando con éxito las pruebas de estimulación de marcha, reposo ruidoso y sacudidas, demostrando la atenuación de falsos positivos frente al detector basado únicamente en umbrales de amplitud temporal.

\subsection{Modelo de Machine Learning (CNN 1D HAR + Fall Detection)}

\subsubsection{Descripción}

Modelo secuencial optimizado (TinyML) integrado a bordo para la clasificación automática de actividades inerciales.

\subsubsection{Entrada y muestreo}

El IMU BMI160 se muestrea físicamente a 100\,Hz en \texttt{har\_task}. Para conformar la entrada del modelo, las muestras consecutivas se promedian, reduciendo el ruido de alta frecuencia y resultando en una señal homogénea de 50\,Hz. La normalización a formato flotante $[-1.0, 1.0]$ se realiza en runtime mediante división por 32768 sobre el buffer de inferencia de 200 muestras. La ventana física abarca 4,0\,s con un traslape del 50\,\% (100 muestras), disparando una predicción inercial cada 2,0\,s. El tensor cuantizado de entrada posee dimensiones de $(200, 6)$ ocupando 1,2\,KB.

La tarea \texttt{har\_task} se configuró pinned de forma asíncrona al \textbf{Core 1} con prioridad 4, evitando que los 8--20\,ms requeridos por la inferencia matemática interrumpan los ciclos del refresco de la pantalla (Core 0, 30 FPS) o interfieran con los descriptores BLE. La optimización se realizó integrando la librería de Espressif \texttt{esp\_nn}, la cual utiliza instrucciones vectoriales Xtensa LX7 para acelerar la computación de convoluciones INT8.

\subsubsection{Entrenamiento}

Se recopiló un dataset de 27 sesiones de IMU (12 reposo, 8 caminata regular, 7 trote periódico) grabadas físicamente con el entorno de captura de datos sobre la muñeca. La clase \textit{fall} se entrenó de forma sintética a partir de un modelo dinámico de caída libre de tres etapas ($0g$ de aceleración $\to$ impacto $>3g$ $\to$ reposo inercial post-caída). El entrenamiento se ejecutó en Keras mediante el script \texttt{tools/train\_har\_cnn.py} aplicando técnicas de data augmentation (rotación angular de ejes inerciales $\pm$15° y jitter de ruido blanco de 1\,\%).

\subsubsection{Resultados}

\begin{itemize}
    \item Modelo compilado e integrado como array de C estático en \texttt{har\_model.c}.
    \item Tiempo de inferencia real medido en bench: 8,2\,ms promedio, con picos máximos estables de 14,1\,ms.
    \item Validation accuracy consolidada en holdout split: 93,4\,\% (resting 100\,\%, walking 95\,\%, running 91\,\%, fall 87\,\%).
    \item Ocupación real medida de la arena TFLite: 88\,KB.
    \item Carga CPU medida en Core 1: 4,2\,\% promedio, disipando la preocupación por la degradación del procesador.
\end{itemize}

\subsection{PCB Carrier SupaClock v1}

\subsubsection{Descripción}

Constituye el soporte físico integrado de dos capas que interconecta el módulo MCU, cargador interno, conectores e interfaces.

\subsubsection{Decisiones de diseño}

Se descartó la versión preliminar y se trazó una nueva placa KiCad en \texttt{hardware/SupaClock\_Carrier/} ajustada rigurosamente a las tolerancias físicas del laboratorio Capstone PUC (fresadora LPKF ProtoMat S64). Se adoptaron anchos de pista generosos de 0,4\,mm y diámetros mínimos de taladro de 0,8\,mm. Se omitió la máscara de soldadura (soldermask) y serigrafía debido a restricciones de manufactura de banco, y se utilizaron extensas zonas poligonales de cobre en la cara BOTTOM para acelerar los tiempos de fresado por remoción mecánica. Se implementó una arquitectura de zócalo (pin sockets 1x7+1x7 through-hole) para alojar e intercambiar con facilidad la placa XIAO S3.

\subsubsection{Cálculos eléctricos}

Se estimó el ancho de pista mínimo de alimentación para soportar los picos transitorios máximos de corriente de arranque sin superar un aumento de temperatura admisible de 10\,°C. Utilizando la norma IPC-2221 para pistas externas con cobre estándar de 1\,oz/ft$^2$ (35\,$\mu$m de espesor) y un pico esperado de $I_{max} = 150$\,mA (incluyendo display e inferencia inercial concurrente):
$$A = \left( \frac{I}{k \cdot \Delta T^{0.44}} \right)^{1/0.725} = \left( \frac{0.15}{0.048 \cdot 10^{0.44}} \right)^{1.379} \approx 0.0076\,\text{mm}^2$$
$$w = \frac{A}{t \cdot 1.378} = \frac{0.0076}{0.035 \cdot 1.378} \approx 0.16\,\text{mm}$$

El ancho físico mínimo requerido por la fresadora LPKF (0,4\,mm) provee un margen de seguridad de más del doble del límite teórico calculado, asegurando una bajísima resistencia e inductancia de pista.

\subsubsection{Resultados}

\begin{itemize}
    \item Plano de diseño finalizado: dimensiones de placa 98$\times$79\,mm con 0 nets sin conectar.
    \item Generación exitosa de archivos Gerber y de taladrado embalados en \texttt{SupaClock\_Carrier\_LPKF\_V2\_G10.zip} listos para fresado.
    \item Reporte DRC libre de violaciones de espaciado o ruteo bloqueantes. 26 advertencias estéticas registradas y catalogadas de forma no bloqueante (ver Sección \ref{sec:anexo_lpkf}).
\end{itemize}

\subsection{Carcasa V2 paramétrica}

\subsubsection{Descripción}

Protección externa e interfaz física optimizada y paramétrica para el wearable, impresa en PLA mediante deposición de filamento fundido (FDM).

\subsubsection{Decisiones de diseño y geometría}

El modelo se definió paramétricamente en OpenSCAD mediante los scripts \texttt{supaclock\_v2\_top\_case.scad} y \texttt{supaclock\_v2\_bottom\_case.scad}. Incorpora curvaturas redondeadas en esquinas ($r\_vert=12$\,mm), chamfer superior e inferior de 1,5\,mm y taper lateral de 2\,mm, maximizando la comodidad en la muñeca. La sujeción física de la correa se resolvió tallando lugs rectangulares unificados a la pared y con slots interiores de 20\,mm aptos para pasadores de resorte estándar de 1,8\,mm.

El corte longitudinal de cerramiento se situó de forma intencional en la cota $Z=4$\,mm, separando el bottom case del top case. Se definieron aperturas alineadas con la PCB carrier: ventana de pantalla de 28$\times$34\,mm en el techo, cutout para el MAX30102 de 22$\times$17\,mm y MAX30205 de 14$\times$10\,mm en la cara inferior, y tres aberturas de Ø 6\,mm para los electrodos M3 de acero inoxidable AISI 304 del ECG.

\subsubsection{Iteración tras impresión}

La primera corrida de impresión arrojó dos discrepancias de acople: la ventana del sensor PPG MAX30102 estaba desplazada 90° debido a una asunción errónea de orientación del zócalo, y el espesor variable en las paredes curvas con chamfer impedía que los orificios atravesaran totalmente la pared del chasis. Se corrigieron las cotas de la ventana a \texttt{cutout\_max30102\_x = 22.0} e \texttt{y = 17.0}, y se extendió la profundidad de corte de los orificios cilíndricos a 16\,mm desde el interior de la cavidad para cruzar holgadamente las zonas de inclinación angular de la carcasa.

\subsubsection{Resultados}

\begin{itemize}
    \item Archivos STL validados y catalogados en \texttt{mechanical/stl/}. Sólidos limpios y manifold.
    \item Impresión física en Prusa MK3S completada en un tiempo total de 13\,h 45\,min (ver Sección \ref{sec:anexo_openscad}).
    \item Desviación de medidas físicas por retracción menor a 0,2\,\% ($w_{real}=97.8$\,mm vs. 98,0\,mm nominal).
    \item Ensamble físico sin holguras mecánicas o atascos en el recorrido del pin de botones.
\end{itemize}

\subsection{Aplicación móvil Flutter}

\subsubsection{Descripción}

Desarrollo e implementación de la app móvil \texttt{app/} en Flutter 3.24 + Dart 3.5, desempeñando el rol de gateway BLE + clinical dashboard del usuario, operando con una filosofía offline-first.

\subsubsection{Arquitectura de servicios}

Los servicios se desacoplaron en 8 singletons inyectados en la jerarquía mediante Provider:
\begin{itemize}
    \item \textbf{\texttt{AuthService}}: Integra Firebase Auth para inicio de sesión seguro.
    \item \textbf{\texttt{BleService}}: Escanea, establece y reconecta la comunicación BLE, parsea tramas TLV, captura telemetría y controla excepciones.
    \item \textbf{\texttt{CsvRecorder}}: Graba streams de ECG e IMU localmente en formato CSV comprimido (.gz), y los transfiere asíncronamente a Firebase Storage.
    \item \textbf{\texttt{DailyRollupService}}: Agrega y computa resúmenes diarios (pasos, HR, temperatura, SpO$_2$, HRV) en Firestore.
    \item \textbf{\texttt{FirestoreService}}: Gestiona lecturas y escrituras seguras en la nube aplicando reglas a nivel de UID de usuario.
    \item \textbf{\texttt{LocalStore}}: Almacena caché local persistente con la base de datos Hive, sincronizando cuando hay red.
    \item \textbf{\texttt{NotificationsService}}: Genera notificaciones locales frente a alertas persistentes.
    \item \textbf{\texttt{PanTompkins}}: Ejecución asíncrona del algoritmo de detección de peaks QRS en un isolate de Dart, arrojando el reporte final de BPM y HRV en menos de 100\,ms.
\end{itemize}

\subsubsection{Doble interfaz}

La aplicación implementa dos modos de interacción conmutables por easter-egg:
\begin{enumerate}
    \item \textbf{Modo Clínico (Usuario):} Visualiza telemetría histórica, tendencias gráficas semanales, e interactúa con capturas de ECG en tiempo real (gráfico de Lorenz, SDNN y RMSSD).
    \item \textbf{Modo Desarrollador:} Muestra osciloscopios con escalado automático para IMU y ECG, envío manual de comandos hex a la característica \texttt{0xFF04}, y grabador CSV clasificado por tipo de actividad inercial para recopilar sets de datos.
\end{enumerate}

\subsubsection{Protocolo BLE y quality gate}

Se respeta el estándar TLV definido por el firmware en \texttt{0xFF02} y el flujo continuo en \texttt{0xFF03}. Para amortiguar falsas alarmas, se incorporó una puerta de calidad (\textbf{quality gate}): las métricas clínicas se procesan si el reporte TLV indica calidad $\ge 60$\,\%, y el evento anómalo debe persistir 60\,s consecutivos antes de disparar alertas sonoras o visuales al usuario.

\subsubsection{Persistencia híbrida y almacenamiento eficiente}

Para mitigar cobros de Firestore por excesiva lectura/escritura y resguardar la experiencia de navegación del usuario, los datos biométricos se leen instantáneamente desde la base de datos Hive de caché local. En paralelo, las trazas pesadas continuas se concatenan y comprimen en formato gzip y se suben directamente como blobs a Firebase Storage, reduciendo el tamaño de transferencia un 70\,\% (compresión típica 3:1).

\subsubsection{Resultados}

\begin{itemize}
    \item Compilación funcional del release APK de Android (28\,MB) probada con éxito.
    \item Descubrimiento y reconexión automática tras pérdida de señal en menos de 5\,s.
    \item Tiempo de procesamiento promedio del algoritmo Pan-Tompkins en isolate Dart: 65\,ms sobre trazas continuas de 30\,s a 500\,Hz.
\end{itemize}

\subsection{UI rediseñada: temas y tipografías}

\subsubsection{Descripción}

Evolución estética de la interfaz gráfica a bordo del ST7789 para enriquecer la experiencia de usuario y optimizar la carga del procesador.

\subsubsection{Sistema de temas}

Se implementó un módulo en \texttt{lib/ui\_theme/} con cuatro temas seleccionables (\texttt{AMOLED}, \texttt{WARM}, \texttt{SLATE}, \texttt{VIVID}), los cuales definen catorce colores semánticos. El tema activo se almacena en el namespace \texttt{supaclock} de NVS; la llamada a \texttt{ui\_theme\_set(id)} actualiza la pantalla en caliente sin requerir el reinicio del wearable.

\subsubsection{Tipografías custom}

Se sustituyeron las fuentes genéricas de LVGL por la familia tipográfica \textbf{Inter} \cite{inter_font}, generando archivos C específicos con la utilidad oficial \texttt{lv\_font\_conv} \cite{lv_font_conv}:
\begin{itemize}
    \item \texttt{ui\_font\_label\_16.c}: Inter Regular 16\,px para etiquetas de texto e íconos chicos.
    \item \texttt{ui\_font\_value\_28.c}: Inter Medium 28\,px para métricas y lecturas.
    \item \texttt{ui\_font\_hero\_56.c}: Inter Bold 56\,px sólo para números grandes de hora y reloj.
    \item \texttt{ui\_font\_icon\_56.c}: Símbolos Material Design de 56\,px para menús principales.
\end{itemize}

\subsubsection{Heap LVGL en PSRAM}

El heap dinámico interno de asignación de objetos de LVGL se trasladó a la PSRAM externa (\texttt{MALLOC\_CAP\_SPIRAM}) mediante la reconfiguración del allocator de memoria. Esto liberó $\approx$16\,KB de SRAM interna, la cual se reasignó para acelerar los buffers DMA del bus SPI.

\subsubsection{Refactor de pantallas en \texttt{lib/supaclock\_ui/}}

Las siete pantallas se separaron de la inicialización de hardware, exponiendo interfaces limpias de refresco bajo protección de mutexes gráficos y registrando los callbacks mediante un struct de acciones.

\subsubsection{Resultados}

\begin{itemize}
    \item Frame rate sostenido de 30 FPS durante la navegación táctil y de botones.
    \item Tiempo de transición entre pantallas de menú menor a 50\,ms.
\end{itemize}

\subsection{Extracto del algoritmo de pasos FFT (\texttt{lib/step\_algorithm/step\_algorithm.c})}\label{sec:anexo_pasos}

El Listado \ref{lst:step_algorithm} muestra la implementación en C del procesamiento espectral de pasos.

\begin{lstlisting}[language=C, caption={Lógica de cómputo FFT en lib/step\_algorithm/step\_algorithm.c.}, label={lst:step_algorithm}]
#if defined(CONFIG_IDF_TARGET_ESP32S3)

#include "esp_dsp.h"
#define FFT_WINDOW_SIZE 128

uint8_t step_algo_update(step_algo_state_t *state, int16_t ax, int16_t ay,
                         int16_t az, int16_t gx, int16_t gy, int16_t gz,
                         uint32_t current_time_ms, bool is_sport_mode) {
  uint8_t new_steps = 0;
  float mag = sqrtf((float)ax*ax + (float)ay*ay + (float)az*az);
  state->accel_mags[state->sample_index] = mag;
  /* ... gating rotacional + DC bias + Hann + FFT radix-2 ... */
  if (state->sample_index >= FFT_WINDOW_SIZE) {
    if (state->max_gyro_val > 400) {
      /* DC bias removal */
      float dc_bias = 0.0f;
      for (int i = 0; i < FFT_WINDOW_SIZE; i++) dc_bias += state->accel_mags[i];
      dc_bias /= FFT_WINDOW_SIZE;
      for (int i = 0; i < FFT_WINDOW_SIZE; i++) state->accel_mags[i] -= dc_bias;
      dsps_wind_hann_f32(state->accel_mags, FFT_WINDOW_SIZE);
      float accel_window[FFT_WINDOW_SIZE * 2];
      for (int i = 0; i < FFT_WINDOW_SIZE; i++) {
        accel_window[i*2]     = state->accel_mags[i];
        accel_window[i*2 + 1] = 0.0f;
      }
      dsps_fft2r_fc32(accel_window, FFT_WINDOW_SIZE);
      dsps_bit_rev_fc32(accel_window, FFT_WINDOW_SIZE);
      float T = (float)(current_time_ms - state->window_start_time_ms) / 1000.0f;
      if (T <= 0.0f) T = (float)FFT_WINDOW_SIZE / 50.0f;
      int min_bin = (int)ceilf(0.75f * T);
      int max_bin = (int)floorf(2.75f * T);
      if (min_bin < 1) min_bin = 1;
      if (max_bin >= FFT_WINDOW_SIZE/2) max_bin = FFT_WINDOW_SIZE/2 - 1;
      float peak_power = 0.0f;
      int   peak_bin   = 0;
      for (int k = min_bin; k <= max_bin; k++) {
        float re = accel_window[k*2], im = accel_window[k*2 + 1];
        float p = re*re + im*im;
        if (p > peak_power) { peak_power = p; peak_bin = k; }
      }
      const float UMBRAL_FFT = 1.0e9f;
      uint8_t detected = (peak_power > UMBRAL_FFT) ? (uint8_t)peak_bin : 0;
      if (is_sport_mode) detected = (uint8_t)((detected + 1) / 2);
      /* ... histéresis 2 ventanas + acumulación ... */
    }
    /* avance overlap 50% en SPORT, reinicio en NORMAL/SAVER */
    state->max_gyro_val = 0;
  }
  return new_steps;
}
#endif
\end{lstlisting}

\subsection{Repositorio y entregables digitales}\label{sec:anexo_repo}

El proyecto completo se aloja en GitHub bajo la rama \texttt{main} en la URL: \texttt{github.com/ArticunoFruna/SupaClock\_IEE2463}.
\begin{itemize}
    \item \texttt{src/}, \texttt{lib/}, \texttt{include/}: código fuente del firmware en ESP-IDF para PlatformIO.
    \item \texttt{app/}: código de la aplicación móvil en Flutter y Dart.
    \item \texttt{firebase/}: funciones de soporte y reglas de bases de datos.
    \item \texttt{hardware/SupaClock\_Carrier/}: diseño de esquemáticos KiCad, ruteado y Gerbers.
    \item \texttt{mechanical/}: scripts en OpenSCAD, archivos STL, dimensiones y renders en 3D.
    \item \texttt{tools/}: scripts en Python para entrenamiento, simulaciones y capturas.
    \item \texttt{data\_ml/}: base de datos inercial recopilada con 27 sesiones registradas en CSV.
    \item \texttt{docs/Entrega3/}: documentos de informe final, Beamer y assets gráficos.
\end{itemize}

Los entregables específicos del Informe de Avance 3 (este informe PDF y la presentación complementaria en Beamer) se autocompilan en caliente mediante el \texttt{Makefile} disponible en la raíz del directorio \texttt{docs/}.
